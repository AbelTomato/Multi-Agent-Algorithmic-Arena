### 2. Docker 官方软件源 TLS 失败

首次使用 Docker 官方软件源安装时失败：

```text
OpenSSL SSL_connect: SSL_ERROR_SYSCALL
```

排查结果：

- 系统时间正常；
- DNS 可以解析 `download.docker.com`；
- TCP 连接可以建立；
- 失败发生在 TLS 握手阶段。

原理：TCP 连接成功不代表 HTTPS 可用。HTTPS 还需要完成 TLS 握手和证书协商，当前服务器到 Docker 官方 CloudFront 的链路在握手阶段失败，因此继续重试同一个软件源没有意义。

处理方式：根据 Alibaba Cloud Linux 3 的官方安装方式，将 Docker CE 软件源切换到阿里云 ECS 内网镜像，并安装 `dnf-plugin-releasever-adapter` 兼容插件。

验证：

```text
Docker CE Stable - x86_64 元数据下载成功
docker-ce、containerd.io、docker-compose-plugin 均可用
```

### 3. Docker Hub Registry 访问超时

Docker 安装后执行测试容器时，首次拉取失败：

```text
Get "https://registry-1.docker.io/v2/":
Client.Timeout exceeded while awaiting headers
```

原理：Docker 软件包仓库和 Docker 镜像仓库是两条不同的访问链路。软件源安装成功，不代表 Docker Hub Registry 一定可访问。服务器可以解析 Registry 域名，但无法完成到 `registry-1.docker.io:443` 的 HTTPS 请求。

处理方式：配置阿里云 ACR 专属镜像加速器，并验证：

```json
{
  "registry-mirrors": [
    "https://uk52zpri.mirror.aliyuncs.com"
  ]
}
```

`hello-world` 随后可以成功拉取并运行，说明 Docker daemon 和基础镜像加速配置有效。

### 4. ACR 加速器无法直接提供 PostgreSQL 镜像

拉取 PostgreSQL 时仍失败：

```text
manifest unknown
```

随后 Docker 回退访问 Docker Hub，最终再次超时。

原理：镜像加速器的 `/v2/` 接口可访问，只说明 Registry 服务在线，不代表目标镜像的 manifest 和所有 layer 已经被该加速器代理或缓存。目标镜像找不到时，Docker 会尝试其他 endpoint；Docker Hub 在当前网络中不可用，于是最终失败。

处理方式：使用 DaoCloud 文档明确提供的前缀方式拉取官方镜像：

```bash
sudo docker pull m.daocloud.io/docker.io/library/postgres:16.4
sudo docker pull m.daocloud.io/docker.io/library/python:3.12-slim
```

两个镜像均成功拉取。Compose 和 Dockerfile 分别改为使用已验证的中转地址，避免构建和启动时回退到 Docker Hub。

### 5. Dockerfile 的 `sed` 精确替换没有生效

尝试替换 Dockerfile 第一行后，检查仍然显示：

```dockerfile
FROM python:3.12-slim
```

原理：从 Windows 工作区上传的文本可能包含 CRLF 换行符。带有行尾字符时，要求整行精确匹配的 `sed` 表达式可能无法命中。

处理方式：不再依赖原始行内容，直接按行号替换：

```bash
sudo sed -i '1cFROM m.daocloud.io/docker.io/library/python:3.12-slim' backend/Dockerfile
```

之后 `head -1 backend/Dockerfile` 确认替换成功，后端镜像构建完成。

### 6. 后端镜像构建耗时较长

后端镜像最终构建成功，但 `pip install` 阶段耗时约 936 秒。

原理：镜像基础层已经从中转源取得，但 Python 依赖仍然需要从 Python Package Index 下载。容器镜像源只解决 Docker image layer 的传输，不会自动加速 `pip` 软件包下载；服务器到 PyPI 的网络较慢，因此依赖安装阶段成为主要耗时点。

结果：构建成功，镜像使用非 root 用户 `app` 运行，启动命令为 Uvicorn。

### 7. 容器健康但宿主机无法访问 8000

初次启动后端时出现矛盾现象：

- 容器 healthcheck 为 `healthy`；
- 容器内部访问 `127.0.0.1:8000/health` 返回 200；
- 宿主机没有监听 `127.0.0.1:8000`；
- `docker port` 无输出。

进一步检查发现：

```text
HostConfig.PortBindings 中存在 127.0.0.1:8000
容器实际 IP 172.18.0.3:8000 可访问
iptables 的 DOCKER 链没有 8000 的 DNAT 规则
```

原理：容器内部健康检查只证明 FastAPI 在容器网络命名空间内正常，不能证明宿主机端口发布成功。Docker 的 `ports` 需要额外创建宿主机到容器的端口转发规则；当转发规则未生成时，容器健康和宿主机访问可以同时出现不同结果。

### 8. `internal: true` 导致端口发布异常

Compose 原始网络配置为：

```yaml
networks:
  arena_private:
    driver: bridge
    internal: true
```

在当前 Docker 26.1.3、Alibaba Cloud Linux 3 和 firewalld 组合下，设置 `internal: true` 后，容器之间可以通信，容器内部健康检查也正常，但宿主机端口发布规则没有正确生成。

处理方式：移除 `internal: true`，保留普通 bridge 网络：

```yaml
networks:
  arena_private:
    driver: bridge
```

安全边界没有因此暴露数据库：

- PostgreSQL 服务没有 `ports` 配置，不发布到宿主机；
- FastAPI 仍只绑定 `127.0.0.1:8000`；
- 公网入口仍然只有 Nginx 的 80/443。

重建网络和容器后验证成功：

```text
127.0.0.1:8000 -> 容器 8000
/health -> HTTP 200
```

### 11. 前端生产构建误用 `localhost:8000`

浏览器初次访问页面时提示无法连接后端，但直接访问公网 API 正常。

根因是本地开发文件：

```env
VITE_API_BASE_URL=http://localhost:8000
```

Vite 会在构建时将 `VITE_*` 变量静态注入 JavaScript。部署后的浏览器请求 `localhost:8000` 时，`localhost` 指向用户自己的电脑，而不是 ECS，因此请求失败。

处理方式：生产构建前移走 `.env.local`，使 `VITE_API_BASE_URL` 为空。前端代码中的：

```typescript
fetch(`${apiBaseUrl}${path}`)
```

最终使用相对路径，例如：

```text
/api/problems
```

浏览器随后通过当前页面的同一域名访问 Nginx，再由 Nginx 代理到 FastAPI。
