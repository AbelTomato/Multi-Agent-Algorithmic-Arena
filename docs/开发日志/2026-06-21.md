### 遇到的问题

- 编写数据库操作测试时，曾把多条题目数据的列表赋值给同一个 `Problem` 对象的字段，例如把 `id` 设置为 `[1, 2, 3]`。
- SQLAlchemy 期望一个 ORM 对象对应数据库中的一行记录，主键应是单个可 hash 值，因此触发 `TypeError: cannot use 'tuple' as a dict key (unhashable type: 'list')`。
- 测试中一开始尝试重新定义新的 `Base`，这会导致新 `Base` 不知道项目里的 `Problem` 模型。

### 解决方式

- 改为创建单个 `Problem` 对象，只赋值单个 `slug`、`title`、`description`。
- 不手动设置 `id`、`created_at`、`updated_at`，交给数据库主键和默认时间字段处理。
- 测试中复用项目已有的 `app.database.Base`，通过 `Base.metadata.create_all` 创建模型对应的数据表。
- 使用 `sqlite+aiosqlite:///:memory:` 作为测试数据库，避免污染真实开发数据库。

### 学到的东西

- 一个 ORM 对象对应数据库中的一行记录；多行记录应该创建多个 ORM 对象，而不是把列表塞进一个对象字段。
- `Problem.__table__.columns` 可以检查模型在 Python 层生成的表结构元数据。
- `Base.metadata.create_all` 会根据模型元数据在数据库中真正创建表。
- 异步 SQLAlchemy 中，`create_all` 需要通过 `conn.run_sync(Base.metadata.create_all)` 执行。
- `select(Problem).where(...)` 可以构造 ORM 查询语句，再通过 `session.execute()` 执行。


### 验证结果

### 遇到的问题

- 导入路径时未从项目包 `app` 开始导入。
- 对于 `get_db()` 返回的 `yield session`，直接使用 `session = await get_db()` 导入。
- 将数据库模型 `Problem` 直接作为请求体使用。
- 初始切片过大，同时实现了 POST 和 GET 接口，导致概念混淆。
- `prefix` 和路由路径重复，写了两遍 `api/`，且写成以 `/` 结尾。
- 与其他项目串线，错误引入 `conftest.py` 中的 `fixture` 写法。
- 引入了当前切片不必要的 `get_db()`、`Problem` 模型。
- 错误填入 `id` 参数至 `client` 的 `get` 方法。
- 未能正确验证 `response.json()` 的结果。

### 解决方式

- 放弃实现数据库相关切片，专注实现最简单的 GET 接口。
- 取消了 `id` 参数。
- 将原本的 `assert response.json() == {[]}` 改为 `assert response.json() == []`。

### 学到的东西

- 对于 `yield` 出的结果，应使用 `Depends` 处理。
- 应创建类似 `problem_create` 结构用于上传题目的 POST 请求。
- 在 `prefix` 中完成前缀路径书写，且末尾不带 `/`。
- 从 `response` 中拿数据应该用 `.json()` 处理。
