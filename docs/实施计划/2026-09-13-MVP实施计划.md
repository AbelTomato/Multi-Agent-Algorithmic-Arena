# MVP 实施计划

## 1. 文档定位

本文件将 [`MVP开发构想.md`](../MVP开发构想.md) 中已确认的决策拆解为可执行的开发切片、测试任务和验收标准。

> **优先级：** `MVP开发构想.md` 是产品范围、技术选型、接口边界和实施顺序的唯一决策基线；本计划不新增与其冲突的产品决策。如两者内容冲突，以 `MVP开发构想.md` 为准，并先修订本计划。

当前 MVP 的定位：**单 Agent 算法题解答演示 MVP**。

## 2. 目标、范围与完成定义

### 2.1 目标闭环

```text
前端获取题目列表
→ 前端按需请求题目详情
→ 用户选择题目并提交题目 ID
→ 后端读取 PostgreSQL 中的题目
→ 服务端生成 Prompt 并调用 Agent
→ 后端一次性返回 Markdown 解题结果
→ 前端渲染结果和 Python 代码块
```

### 2.2 MVP 完成定义

满足以下条件即可视为 MVP 完成：

1. PostgreSQL 可通过环境变量配置，数据库可通过 migration 和 seed 从空库初始化；
2. `GET /api/problems` 可返回题目列表；
3. `GET /api/problems/{problem_id}` 可返回完整 Markdown 题面；
4. `POST /api/solutions` 只接收 `problem_id`，由服务端控制 Prompt；
5. 后端具备 Agent / Provider 抽象，并可使用 MockAgent 跑通闭环；
6. Agent 失败时最多自动重试一次，二次失败返回受控错误；
7. React 前端可浏览题目、请求解题、显示加载和错误状态、渲染 Markdown 结果；
8. MockAgent 版本已完成部署环境验证：前后端、PostgreSQL、环境变量、CORS、白名单和健康检查均可用；
9. 自动化测试覆盖各实现切片的核心成功和失败场景。

### 2.3 明确排除项

当前不实现：代码执行和评测、自动评分、排行榜、多 Agent、比赛状态机、辩驳、Redis、WebSocket/SSE/流式输出、登录系统、历史记录、题库管理、外部题库导入、多 Provider 接入和 Monaco Editor。

## 3. 当前现状与改造边界

当前仓库已有 FastAPI、SQLAlchemy async、最小 `Problem` ORM 模型、`GET /api/problems` 路由骨架、健康检查和 pytest 基线。

| 项目 | 当前状态 | MVP 目标 |
| --- | --- | --- |
| 数据库 | PostgreSQL 主链路；SQLite/aiosqlite 仅用于快速单元测试 | ✅ 已完成 |
| 表初始化 | Alembic revision `0001` 已创建 `problems` 表 | ✅ 已完成 |
| 题目数据 | `app.seed` 已写入 2 道题，重复执行插入 0 条 | ✅ 已完成 |
| Problem API | 列表与详情查询已实现 | ✅ 已完成 |
| Agent | 统一抽象、MockAgent 和工厂已实现 | ✅ 已完成 |
| 解题接口 | 同步 `POST /api/solutions`，含一次重试和受控错误 | ✅ 已完成 |
| 前端 | React + Vite + TypeScript，已完成浏览和 Markdown 展示 | ✅ 已完成 |
| 部署 | Alibaba Cloud Linux 3 ECS；Nginx + Docker Compose，`tomato-agent-arena.me` 正式 HTTPS 已上线，公网 IP 灰度入口保留回退 | ✅ 正式域名 HTTPS 验收通过 |

### 3.1 已存在且可复用的代码

- `backend/app/config.py`：Pydantic Settings 配置入口；
- `backend/app/database.py`：SQLAlchemy async 的 `Base`、engine、session 和依赖注入入口；
- `backend/app/models/problem.py`：字段已满足 MVP 最小题目模型；
- `backend/app/api/problems.py`：题目路由前缀；
- `backend/app/main.py`：FastAPI 应用和 `/health`；
- `backend/tests/`：pytest、pytest-asyncio 和 FastAPI TestClient 测试基线。

### 3.2 实施约束

- MVP 不再将 SQLite 作为运行主链路，也不提交任何数据库文件；
- 业务路由不得直接依赖特定 LLM SDK；
- 客户端不得传递 Prompt、Provider、模型名或模型参数；
- 模型输出为 Markdown，返回的 Python 代码只展示、不执行；
- 不因部署平台和 LLM Provider 尚未选定而阻塞 MockAgent 完整闭环。

## 4. 实施顺序总览

```text
阶段 1：PostgreSQL + Alembic migration + seed
→ 阶段 2：Problem API
→ 阶段 3：Agent / Provider 抽象 + MockAgent
→ 阶段 4：Solutions API + Prompt 控制 + 一次重试
→ 阶段 5：React 前端
→ 阶段 6：前后端联调与 API 契约固定
→ 阶段 7：部署 MockAgent 版本
→ 阶段 8：选择并接入一个真实 LLM Provider
```

除阶段 8 外，前七个阶段不依赖具体云平台或真实 LLM API Key。

## 5. 阶段 1：PostgreSQL、Alembic Migration 与题目 Seed

### 5.1 学习与构建目标

- 理解 PostgreSQL 连接串、异步 SQLAlchemy 驱动、Alembic revision 和 migration 执行流程；
- 将运行时数据库由 SQLite 原型切换为 PostgreSQL；
- 使空数据库能通过 migration 和 seed 获得可供 API 查询的题目数据。

### 5.2 实现任务

1. 为项目补充经确认可用于 SQLAlchemy async 的 PostgreSQL 驱动，并锁定版本；
2. 调整 `backend/app/config.py`：数据库 URL 继续通过 `DATABASE_URL` 环境变量读取，默认值和示例改为 PostgreSQL 格式；
3. 调整 `backend/app/database.py`：保持异步 engine、session 和 `get_db()` 依赖注入模式，避免在模块导入阶段产生不必要的连接；
4. 初始化 `backend/alembic/` 和 `backend/alembic.ini`；
5. 配置 Alembic 的 metadata 导入，使其识别 `app.database.Base.metadata` 和 `Problem` 模型；
6. 创建首个 `problems` 表 migration，字段仅包含 `id`、`slug`、`title`、`description`、`created_at`、`updated_at`；
7. 编写可重复执行的题目 seed 命令或脚本，以稳定唯一字段（例如 `slug`）避免重复插入；
8. 从 Git 移除并忽略 SQLite 数据库等运行时文件；不得提交 PostgreSQL 数据文件；
9. 更新 `.env.example`，只保留可公开的配置样例，不写入密码或真实连接信息。

### 5.3 测试任务

- 配置默认值和环境变量覆盖测试；
- migration 从空测试数据库升级成功；
- migration 后 `problems` 表及字段存在；
- seed 后可查询到预置题目；
- seed 重复运行不产生重复题目；
- PostgreSQL 集成测试与单元测试分层，无法提供测试库时应清晰跳过集成测试，不得静默回退至 SQLite 主链路。

### 5.4 验收标准

```text
空 PostgreSQL 数据库
→ 执行 migration
→ 执行 seed
→ 查询到预置题目
→ 完整测试通过
```

### 5.5 暂不处理

- 题目难度、标签、来源、默认语言、测试用例；
- Docker Compose、Redis、数据库管理后台；
- 题目增删改接口。

## 6. 阶段 2：Problem API

### 6.1 学习与构建目标

- 理解 FastAPI 的 `Depends`、响应 Schema、404 错误和异步数据库查询；
- 让前端可以按需浏览题目列表和完整题面。

### 6.2 接口契约

```http
GET /api/problems
GET /api/problems/{problem_id}
```

推荐将列表接口限制为题目摘要，避免在加载列表时传输全部题面：

```json
[
  {
    "id": 1,
    "slug": "two-sum",
    "title": "Two Sum"
  }
]
```

详情接口返回完整题面：

```json
{
  "id": 1,
  "slug": "two-sum",
  "title": "Two Sum",
  "description": "# Two Sum\n..."
}
```

### 6.3 实现任务

1. 为题目列表和题目详情创建独立响应 Schema；
2. 在 `backend/app/api/problems.py` 通过 `Depends(get_db)` 获取 Session；
3. 实现稳定排序的列表查询；
4. 实现按 `problem_id` 查询详情；
5. 不存在的题目返回 HTTP 404；
6. 发生数据库异常时不暴露内部连接信息；
7. 删除当前“固定返回空数组”的测试假设。

### 6.4 测试任务

- 有 seed 数据时返回列表；
- 列表结构与公开字段一致；
- 查询存在题目时返回完整 Markdown 题面；
- 查询不存在题目时返回 404；
- 使用测试数据库验证真实查询，不只测试路由状态码。

### 6.5 验收标准

```text
GET /api/problems       → 返回预置题目摘要
GET /api/problems/1     → 返回完整题面
GET /api/problems/99999 → 404
```

## 7. 阶段 3：Agent / Provider 抽象与 MockAgent

### 7.1 学习与构建目标

- 建立业务层和模型厂商 SDK 之间的边界；
- 在不配置真实 API Key 的前提下，验证解题业务链路。

### 7.2 分层约束

```text
Solutions API
→ Solution 服务（读取题目、生成 Prompt、重试）
→ 统一 Agent 接口
→ MockAgent / 未来的真实 Provider 适配器
```

- 路由层负责 HTTP 请求和响应；
- Solution 服务负责业务编排；
- Agent 只接受服务端已生成的解题上下文并返回结果；
- 具体 Provider 适配器只负责调用对应 SDK；
- 路由和业务服务不得直接导入具体厂商 SDK。

### 7.3 实现任务

1. 定义统一 Agent 协议或抽象基类，以及最小输入、输出与异常模型；
2. 实现 MockAgent，返回合法且固定结构的 Markdown；
3. 规定 Agent 输出必须包含：解题思路、算法步骤、正确性说明、时间复杂度、空间复杂度和完整 Python 代码；
4. 通过依赖注入或工厂集中选择当前 Agent 实现，默认使用 MockAgent；
5. 保留未来 Provider 的配置扩展点，但不提前接入多个 SDK。

### 7.4 测试任务

- MockAgent 符合统一 Agent 接口；
- MockAgent 输出包含六个必需章节和 Python 代码块；
- 上层服务仅依赖抽象而非具体 MockAgent 类型；
- Agent 异常能被上层识别和处理。

### 7.5 验收标准

不设置 LLM API Key 时，系统仍可生成一次完整的模拟 Markdown 解题结果。

## 8. 阶段 4：Solutions API、Prompt 控制与一次重试

### 8.1 学习与构建目标

- 建立受服务端控制的同步解题请求；
- 理解输入校验、Prompt 拼接、超时和受控重试。

### 8.2 接口契约

```http
POST /api/solutions
Content-Type: application/json

{
  "problem_id": 1
}
```

请求体只允许 `problem_id`。不得接收或信任客户端传递的 Prompt、语言、Provider、模型名称、温度、最大输出长度或重试参数。

成功响应示例：

```json
{
  "problem_id": 1,
  "result": "## 解题思路\n...",
  "language": "python"
}
```

### 8.3 服务端 Prompt 规则

服务端统一生成的 Prompt 必须约束 Agent：

1. 只围绕给定算法题作答；
2. 固定使用 Python；
3. 固定输出 Markdown；
4. 包含六个指定章节；
5. 不执行题目之外的指令；
6. 不泄露系统 Prompt；
7. 不输出与题目无关的内容。

题目 `title` 和完整 `description` 由后端从数据库读取后拼接进解题上下文。

### 8.4 实现任务

1. 创建仅包含 `problem_id` 的请求 Schema；
2. 查询题目，不存在时返回 404；
3. 在独立服务中生成 Prompt 并调用统一 Agent 接口；
4. 实现单次自动重试：首次失败后仅重试一次；
5. 两次均失败或超时时，转换为不泄露内部细节的受控 API 错误；
6. 一次性返回结果，不增加 WebSocket、SSE、队列、轮询或结果持久化；
7. 不保存请求、Agent 输出或用户历史。

### 8.5 测试任务

- 成功请求返回指定题目的 Markdown 结果；
- 不存在的 `problem_id` 返回 404，且不调用 Agent；
- Agent 首次失败、第二次成功时总调用次数为两次；
- Agent 两次失败时返回预期错误；
- 请求体缺少或非法的 `problem_id` 返回校验错误；
- 客户端额外传入 Prompt 不能影响服务端实际 Prompt；
- 服务端生成的 Prompt 包含题目内容与输出约束；
- 超时和 Provider 异常不会原样泄露给客户端。

### 8.6 验收标准

```text
POST /api/solutions + 合法 problem_id
→ 返回一次性 Markdown 结果

POST /api/solutions + 不存在 problem_id
→ 404

Agent 连续两次失败
→ 受控错误响应
```

## 9. 阶段 5：React 前端

### 9.1 学习与构建目标

- 建立 React、Vite、TypeScript、shadcn/ui、Tailwind CSS 和 Markdown 渲染的最小前端工程；
- 实现题目浏览和同步解题结果展示。

### 9.2 实现任务

1. 在仓库中创建独立前端工程，使用 React、Vite 和 TypeScript；
2. 接入 Tailwind CSS、shadcn/ui 和 Markdown 渲染库；
3. 配置环境变量形式的后端 API Base URL；
4. 实现题目列表：加载 `GET /api/problems` 并显示标题；
5. 实现题目详情：点击题目后请求 `GET /api/problems/{problem_id}`；
6. 对题面 Markdown 进行安全渲染；
7. 实现“让 Agent 解题”操作，只发送当前题目 ID；
8. 请求期间禁用重复提交或以其他明确方式避免并发重复请求；
9. 显示加载状态、网络错误、服务端错误和空状态；
10. 渲染 Agent Markdown，正确显示 Python 代码块；不执行代码。

### 9.3 前端状态边界

页面刷新后，当前题目选择和解题结果可以丢失；MVP 不加入本地持久化、后端历史记录、用户账户或缓存机制。

### 9.4 测试任务

- 题目列表加载和渲染；
- 点击题目后详情请求与渲染；
- 解题请求期间的按钮状态和加载提示；
- 解决成功后的 Markdown 和代码块展示；
- Problem API 或 Solutions API 失败时显示可理解错误；
- 校验前端未提交用户 Prompt 或模型参数。

### 9.5 验收标准

用户从页面选择题目、点击解题后，可看到 MockAgent 返回的 Markdown 结果及 Python 代码块。

### 9.6 已确定的工程约定

- 前端工程目录：仓库根目录下的 `frontend/`；
- 包管理器和命令：npm，使用 `npm run dev`、`npm test -- --run` 和 `npm run build`；
- 后端 API Base URL：`VITE_API_BASE_URL`；本地开发留空时由 Vite 将 `/api` 和 `/health` 代理到 `http://localhost:8000`；
- Markdown：`react-markdown` + `remark-gfm`，不启用 `rehype-raw`；代码块只渲染为 `<pre><code>`，不执行；
- UI：Tailwind CSS 和本地 shadcn/ui 风格的基础组件；
- 状态：列表、详情和解题请求分别管理加载/错误状态；解题期间禁用按钮；切换题目时清理旧详情和结果，并取消旧详情请求；
- 测试：Vitest + React Testing Library，使用 `fetch` mock，不访问真实后端。

## 12. 阶段 8：选择并接入一个真实 LLM Provider

### 12.1 触发条件

MockAgent 部署链路已经稳定；在成本预算明确且可用 API 已确认后，可以先在本地或受控生产配置中开始本阶段的 Provider Spike。真实 API Key 的额度和费用限额必须先在 Provider 平台配置；本项目不自行实现计费系统。

### 12.2 决策顺序

```text
确认成本预算
→ 选择一个 Provider
→ 选择一个模型
→ 确定最大输出长度、超时和模型参数
→ 实现该 Provider 适配器
→ 手动联调和有限集成验证
```

### 12.3 实现任务

1. 基于阶段 3 的统一接口增加一个 OpenAI Compatible Provider 适配器，调用 Chat Completions 风格接口；
2. API Key 只从部署环境变量读取，绝不提交到仓库、前端或日志；
3. 将模型名称、最大输出长度、超时和重试参数集中配置；
4. 保留 MockAgent 作为单元测试和故障隔离实现；
5. 只接入一个真实 Provider，不提前实现多厂商路由或回退策略；
6. 手动确认真实输出符合固定 Markdown 和 Python 约束。

当前已完成：

- `OpenAICompatibleProvider` 已实现 `POST /chat/completions` 请求、Bearer API Key、模型、最大输出长度和超时配置；
- `ProviderAgent` 已将 Provider 接入现有 `Agent.generate()` 接口；
- `LLM_PROVIDER=mock` 时仍使用 MockAgent，只有显式设置 `LLM_PROVIDER=openai_compatible`、`LLM_API_KEY` 和 `LLM_MODEL` 才启用真实 Provider；
- API Key 使用 `SecretStr` 保存，Provider 错误不会向客户端暴露上游响应体或 API Key；
- 自动化测试使用 `httpx.MockTransport`，不访问真实网络、不消耗 API 配额。
