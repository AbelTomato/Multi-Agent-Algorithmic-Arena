# 项目开发协作规则

## 适用范围

本规则适用于本项目中由 Cline 执行的所有代码、测试、文档、配置和运维辅助工作。规则优先级高于一般实现偏好；如果用户在当前对话中明确提出更严格的要求，以更严格的要求为准。

## 一、核心业务代码变更管理

### 1. 核心业务代码范围

以下内容默认视为核心业务代码：

- 业务用例、服务层、领域逻辑和状态机；
- API 路由、请求/响应契约和错误处理；
- 数据模型、数据访问逻辑和持久化相关代码；
- Agent、Provider、Judge、Contest 等核心模块；
- 会影响业务行为、数据一致性、安全性或外部接口兼容性的配置；
- 与上述代码直接相关的核心测试、fixture 和测试数据构造逻辑。

无法判断是否属于核心业务代码时，按核心业务代码处理，并保持清晰的变更范围。

### 2. 实现后的变更记录要求

每次完成核心业务代码后，Cline 必须在最终回复中单独列出“核心业务代码变更说明”，至少包含：

1. 新增或修改的完整绝对路径；
2. 每个文件中需要重点审查的类、函数、接口或代码区段；
3. 本次实现的业务行为变化；
4. 已知风险、假设和未覆盖场景。

完成实现并执行必要验证后，Cline 可以直接报告实现结果，不以额外的用户审查作为交付前置条件。

### 3. 实现边界

Cline 可以完成必要的代码实现、静态检查和非破坏性测试，但必须保留清晰的变更范围。不得为了规避审查或降低可维护性：

- 将核心逻辑拆到不易发现的辅助文件；
- 将业务逻辑隐藏在测试、脚本或配置中；
- 擅自扩大与当前任务无关的重构范围；
- 覆盖、回滚或删除用户已有的未提交改动。

## 二、高危操作必须先审批

### 1. 高危操作定义

以下操作均属于高危操作：

- 执行数据库 migration、upgrade、downgrade 或 schema 变更；
- 执行 seed、批量插入、更新、删除、清空、重建索引或修改数据库权限；
- 对生产、共享、远程或不可逆环境执行任何写操作；
- 删除项目文件、批量重命名、覆盖用户文件或执行可能丢失数据的命令；
- 修改密钥、凭据、权限、部署环境或外部服务状态；
- 执行可能产生费用、触发部署或影响其他开发者环境的操作。

执行任何上述高危操作前，Cline 必须说明操作目标、范围、影响和恢复方式，并获得用户针对该具体操作的明确许可。未获得明确许可时不得执行。

### 2. 数据库操作审批流程

执行任何实际数据库写操作前，Cline 必须：

1. 说明操作目标、目标环境、完整命令和预期影响；
2. 说明是否可逆、是否需要备份以及失败后的恢复方式；
3. 明确等待用户批准，或确认由用户亲自执行。

未获得用户明确批准时，Cline **不得**执行实际数据库变更。可以进行以下非写入工作：

- 读取代码、配置和 migration 文件；
- 分析 SQL 或 migration 内容；
- 生成待用户审查的 migration 文件；
- 编写数据库测试和校验脚本；
- 提供由用户手动执行的命令。

“继续”“做完它”“按计划执行”等一般性表述不等同于数据库写操作批准。必须得到针对具体操作的明确批准。

### 3. 测试数据库例外

测试数据库也必须区分操作类型：

- 由自动化测试在隔离、临时数据库中创建和销毁测试结构，可在测试所需范围内执行；
- 连接用户本地、共享或持久化数据库执行 migration、seed、写入、删除前，仍须获得明确批准；
- 无法确认数据库是否隔离时，按高危操作处理并停止写入。

## 三、测试必须以用户 Spec 为准

### 1. 职责分工

- 用户负责提供测试 Spec、业务验收意图、边界条件和预期行为；
- Cline 负责根据 Spec 补充和完善测试代码，包括 fixture、mock、参数化、断言、测试数据构造和测试组织；
- Cline 不得在没有用户 Spec 的情况下擅自创造关键业务规则、验收标准或具有业务含义的预期结果。

### 2. 缺少 Spec 时的处理

如果用户没有提供足够的测试 Spec，Cline 必须：

1. 先列出缺失的业务行为、输入边界和预期结果；
2. 可以提供候选测试场景供用户确认；
3. 仅可补充不改变业务含义的基础测试，例如导入、类型、固定配置和明显的错误传播；
4. 不得把自行假设的场景标记为完整业务测试覆盖。

### 3. 测试报告要求

验证结束后必须报告：

- 执行的完整命令和执行目录；
- 通过、失败、跳过数量；
- 失败测试的明确原因；
- 因缺少 Spec 尚未覆盖的场景；
- 数据库集成测试是否实际执行，还是因环境缺失而跳过。

测试通过不等于业务正确，也不等于用户需求已完成验收。

## 四、标准工作流程

涉及代码变更时，Cline 应按以下顺序执行：

1. 读取 README、相关设计文档、现有实现和测试；
2. 检查工作区状态，避免覆盖用户未提交改动；
3. 明确本次变更是否涉及核心业务代码或高危操作；
4. 如涉及测试，确认用户 Spec；缺失时先列出待确认项；
5. 实施最小必要变更；
6. 执行不涉及高危操作的静态检查和测试；
7. 对高危操作只提供方案和命令，除非已获得明确批准；
8. 重新读取或检查所有修改文件；
9. 任务执行完成后，按“开发日志要求”写入当日开发日志；
10. 在最终回复中提交变更清单、开发日志状态、审批状态和测试报告。

## 五、最终交付格式

涉及代码或配置变更时，最终回复必须包含以下部分：

### 修改文件

列出所有新增、修改和删除文件的完整绝对路径。

### 读取文档

列出为本次任务读取过的 README、设计文档、计划文档或项目规则文件。

### 文档回填

列出本次更新的文档；如果没有更新，明确写明 `NOT BACKFILLED` 及原因。

### 核心业务代码变更说明

如果本次涉及核心业务代码，必须列出文件、重点代码点、行为变化和风险。如果不涉及，明确写明“不涉及核心业务代码”。此部分仅用于变更记录，不构成额外交付前置条件。

### 高危操作审批状态

明确说明：

- 是否涉及高危操作；
- 是否执行了数据库或其他外部环境写操作；
- 若未执行，说明用户需要亲自执行的命令或后续步骤；
- 若已批准，记录批准对应的具体操作范围。

### 测试结果

列出测试命令、通过数/总数、失败数、跳过数，以及 Spec 缺口和集成测试状态。

## 六、开发日志要求

- 每项任务执行完成后，必须写入当日开发日志；
- 写入日志前必须查询当前时间，不得直接依据系统默认时区或主观日期判断日志文件名；
- 当前时间统一以 `Asia/Shanghai`（Shanghai）时区为准，并据此确定 `YYYY-MM-DD`；
- 日志文件写入 `docs/开发日志/YYYY-MM-DD.md`，同一天的多次开发记录合并到同一个文件；
- 日志应尽量简短，只保留可恢复上下文所需的关键信息，包括任务目标、实际改动、关键命令及验证结果、未完成事项或后续步骤；
- 不重复粘贴大段代码、完整工具输出或无助于恢复上下文的过程性内容；
- 应遵循 `docs/开发日志/README.md` 中的目录规则和日志模板。

## 七、禁止事项

Cline 不得：

- 未经明确批准执行数据库写操作或不可逆环境操作；
- 把测试通过当作业务正确或用户需求验收完成；
- 在缺少用户 Spec 时擅自确定关键业务验收逻辑；
- 忽略或覆盖用户已有未提交改动；
- 隐瞒未验证、跳过、失败或未回填的内容；
- 在最终回复中省略核心业务变更说明、开发日志状态或高危操作审批状态。
